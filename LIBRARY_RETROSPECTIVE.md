# Ретроспектива використання зовнішніх бібліотек

Лабораторна робота №3, CodeLearn Studio. Для кожної бібліотеки нижче описано, яке завдання
вона розв'язує в проєкті, чому обрали саме її, що сподобалось, що ні, і якими ресурсами
ми користувались. Версії зафіксовано в `requirements.txt`.

| Бібліотека | Де використовується | Навіщо |
|---|---|---|
| PyQt5 | `src/gui/` | Графічний інтерфейс, вкладки, фонові потоки |
| SQLAlchemy | `src/database/` | Збереження прогресу студентів і результатів бенчмарку в SQLite |
| numpy | `src/core/benchmark.py` | Генерація вхідних даних, статистика замірів, оцінка складності |
| matplotlib | `src/gui/panels/dashboard_panel.py`, `benchmark_panel.py` | Графіки |
| networkx | `src/gui/panels/graph_panel.py` та ін. | Розкладка графів, граф знань |
| pytest, pytest-cov | `tests/` | Модульні та GUI-тести, покриття |

## 1. PyQt5 — графічний інтерфейс

### Завдання
Десктопний застосунок із вкладками (сортування, порівняння алгоритмів, структури даних, графи,
вправи, прогрес), покроковою анімацією, світлою і темною темою та фоновими задачами, які не
блокують вікно (перевірка рішень, бенчмарк).

### Чому PyQt5
- Повноцінний набір віджетів: `QTabWidget`, `QTableWidget`, `QSplitter`, `QListWidget` з
  прапорцями тощо. У tkinter більшість із цього довелось би писати вручну.
- `QPainter` дозволяє малювати візуалізації структур даних самостійно, з повним контролем.
- Офіційно підтримується бекендом matplotlib (`backend_qt5agg`), тож графіки вбудовуються
  прямо у вкладки.
- Механізм сигналів і слотів добре лягає на ООП: панелі не знають одна про одну, а спілкуються
  сигналами (`attemptRecorded`, `progressReset`, `resultsSaved`).

### Позитивні аспекти
- ✓ Сигнали між потоками доставляються через чергу подій головного потоку, тому результат із
  `QThread` можна безпечно показувати в GUI без ручної синхронізації.
- ✓ Таблиці стилів QSS: одна функція `stylesheet(theme)` перефарбовує весь застосунок.
- ✓ `QSettings` зберігає геометрію вікна, тему, вкладку й поточного студента без власного коду.
- ✓ Платформа `offscreen` дозволяє запускати GUI-тести і робити скріншоти без дисплея.

### Негативні аспекти
- ✗ Виняток, що вилетів із `QThread.run()`, аварійно завершує весь процес, тож усе в `run()`
  треба загортати в `try/except`.
- ✗ Python-атрибут із тим самим ім'ям, що й віртуальний метод Qt, ламає застосунок. Наприклад,
  властивість `metric` у віджеті перекрила `QPaintDevice.metric()`, і Qt під час
  перемальовування викликав рядок як функцію (`TypeError` → `Aborted`). Помилка проявлялась
  лише в повному прогоні тестів, коли змінювалась тема.
- ✗ Деякі розміри з QSS неочевидні: `QHeaderView.minimumSectionSize` під нашими стилями був
  170 px, і колонку не вдавалося звузити, поки не викликати `setMinimumSectionSize()`.
- ✗ Важкий пакет (~60 МБ), ліцензія GPL; документація здебільшого для C++, назви методів
  доводиться перекладати на Python самостійно.

### Ресурси
- Документація Qt 5: https://doc.qt.io/qt-5/
- Довідник PyQt5: https://www.riverbankcomputing.com/static/Docs/PyQt5/
- Посібник: https://www.pythonguis.com/pyqt5-tutorial/
- Багатопотоковість: https://doc.qt.io/qt-5/thread-basics.html

## 2. SQLAlchemy — база даних

### Завдання
У ЛР2 прогрес зберігався в одному JSON-файлі з одним студентом. У ЛР3 потрібно було
підтримати кількох студентів, зберігати історію спроб і результати бенчмарку, а також
робити агрегатні запити (рейтинг студентів).

### Що зроблено
- `src/database/models.py`: ORM-моделі `Student`, `ExerciseAttempt`, `AlgorithmRun`
  у стилі SQLAlchemy 2.0 (`DeclarativeBase`, `Mapped[...]`, `mapped_column`) зі зв'язками
  `relationship` і каскадним видаленням.
- `src/database/database.py`: клас `Database` (engine, фабрика сесій, контекстний менеджер
  сесії-транзакції з `commit`/`rollback`, увімкнення зовнішніх ключів у SQLite).
- `src/database/repository.py`: абстрактний `ProgressRepository` і дві реалізації,
  `JsonProgressRepository` і `SqlProgressRepository`. GUI працює лише з інтерфейсом, тому
  сховище можна підмінити без змін у панелях (поліморфізм, патерн «Репозиторій»).
- Одноразова міграція: під час першого запуску старий `progress.json` імпортується в
  `codelearn.db` і перейменовується в `progress.json.imported`.
- `AlgorithmRunRepository` зберігає результати вкладки «Порівняння».

### Чому SQLAlchemy
- ORM дозволяє працювати з таблицями як із класами Python, що природно для ЛР з ООП.
- Не прив'язує до конкретної СУБД: зараз SQLite (вбудований у Python, без сервера), а
  перейти на PostgreSQL можна, змінивши тільки URL.
- Запити будуються в Python (`select`, `func.max`, `group_by`, `outerjoin`), без склеювання
  SQL-рядків і, отже, без SQL-ін'єкцій.
- БД у пам'яті (`sqlite://`) робить тести швидкими й ізольованими.

### Позитивні аспекти
- ✓ Стиль 2.0 з анотаціями `Mapped[int]` добре читається і перевіряється IDE.
- ✓ `relationship(..., cascade="all, delete-orphan")`: видалення студента прибирає всі
  його спроби й заміри, а тест це підтверджує.
- ✓ Контекстний менеджер сесії гарантує відкат транзакції при помилці.
- ✓ Агрегатні запити (рейтинг: сума найкращих балів за кожну вправу) пишуться декларативно.

### Негативні аспекти
- ✗ Високий поріг входу: engine, connection, session, identity map, стани об'єктів (expired,
  detached). Наприклад, без `expire_on_commit=False` об'єкти після закриття сесії стають
  недоступними для читання.
- ✗ SQLite за замовчуванням ігнорує зовнішні ключі, їх треба вмикати через
  `PRAGMA foreign_keys=ON` у слухачі події `connect`.
- ✗ БД у пам'яті за замовчуванням своя для кожного з'єднання, тож для тестів потрібен
  `StaticPool`, інакше друга сесія бачить порожню базу.
- ✗ Багато застарілих прикладів в інтернеті використовують API 1.x (`declarative_base`,
  `session.query`), який у 2.0 працює інакше або видає попередження.

### Ресурси
- Документація SQLAlchemy 2.0: https://docs.sqlalchemy.org/en/20/
- Unified Tutorial: https://docs.sqlalchemy.org/en/20/tutorial/index.html
- ORM Quick Start: https://docs.sqlalchemy.org/en/20/orm/quickstart.html
- Зовнішні ключі в SQLite: https://docs.sqlalchemy.org/en/20/dialects/sqlite.html#foreign-key-support

## 3. numpy — числові обчислення

### Завдання
Вкладка «Порівняння» заміряє швидкодію алгоритмів сортування на масивах різного розміру
й типу та оцінює їхню складність за експериментальними даними.

### Що зроблено (`src/core/benchmark.py`)
- Генератори вхідних даних як ієрархія класів `InputGenerator` → `RandomInput`,
  `SortedInput`, `ReversedInput`, `NearlySortedInput`, `FewUniqueInput` на основі
  `numpy.random.Generator` з фіксованим seed, тому результати відтворювані.
- `make_sizes()`: рівномірна сітка розмірів через `numpy.linspace`.
- Статистика повторних замірів: `numpy.mean`, `numpy.std(ddof=1)` (стовпчики похибок на графіку).
- Оцінка складності:
  - нахил прямої в log-log масштабі через `numpy.polyfit(log n, log v, 1)`: якщо v ≈ c·nᵏ,
    нахил дорівнює k;
  - вибір найближчої моделі (O(n), O(n log n), O(n²)) методом найменших квадратів
    `numpy.linalg.lstsq` з відносною похибкою, щоб великі n не домінували.
- Тести перевіряють, що за кількістю порівнянь Bubble Sort визначається як O(n²),
  Merge/Heap Sort як O(n log n), а Insertion Sort на відсортованому масиві як O(n).

### Чому numpy
- Векторні операції над масивами набагато коротші й швидші за цикли Python.
- Сучасний API випадкових чисел (`default_rng`) з незалежними генераторами, а не глобальний стан.
- `polyfit` і `lstsq` дають регресію без окремої бібліотеки на кшталт scipy.
- numpy вже є залежністю matplotlib, тож новий пакет не додає ваги.

### Позитивні аспекти
- ✓ Відтворюваність: однаковий seed дає однакові масиви, тож однакові лічильники операцій,
  на що й спираються тести.
- ✓ Лаконічність: оцінка складності займає приблизно 20 рядків.
- ✓ Чудова документація з прикладами для кожної функції.

### Негативні аспекти
- ✗ Наші алгоритми працюють зі списками Python, тому масиви numpy доводиться переводити
  через `.tolist()`. Інакше порівняння `numpy.int64` повільніше і `output == sorted(data)`
  повертає масив, а не bool.
- ✗ Заміри часу шумні на малих n: Merge Sort за часом інколи «виглядає» як O(n). Тому
  складність надійніше оцінювати за кількістю порівнянь, а час показувати з похибкою.
- ✗ Типи numpy (`np.float64`, `np.int64`) не завжди приймаються іншими бібліотеками
  (наприклад, при записі в БД), їх треба явно приводити до `float` / `int`.

- Документація numpy: https://numpy.org/doc/stable/
- Генерація випадкових чисел: https://numpy.org/doc/stable/reference/random/generator.html
- `polyfit`: https://numpy.org/doc/stable/reference/generated/numpy.polyfit.html
- `linalg.lstsq`: https://numpy.org/doc/stable/reference/generated/numpy.linalg.lstsq.html
